# 구현을 따라가며 배우는 단계별 협업 교본

이 교본은 Versioned Finance Core를 구현하면서 사용자가 변경 이유, 코드 흐름, 검증 결과를 직접 이해하고 확인하기 위한 진행 방법이다. 한 단계의 기본 순서는 **계획 → 수정 파일 안내 → 구현 → 핵심 diff 설명 → 테스트 결과 → 정지**다.

여기서 “페어 프로그래밍 방식”은 대화에서 정하는 협업 규칙을 뜻한다. 이 문서를 사용할 때는 아래 시작 요청문으로 적용 범위와 멈추는 지점을 지정한다.

## 1. 바로 시작하는 요청문

다음 내용을 복사하고 `[이번 작업]`만 바꿔서 요청한다.

```text
docs/pair_programming_guide.md를 읽고 단계별 협업 방식으로 진행해줘.
이번 작업: [이번 작업]

먼저 현재 구현 상태와 관련 설계 문서를 확인해줘.
작업을 내가 이해하고 검증할 수 있는 작은 단계로 나눠줘.
이번에는 첫 단계만 구현해줘.

각 단계에서는 다음 순서를 지켜줘.
1. 목적, 입력과 출력, 완료 기준을 설명한다.
2. 수정할 파일과 각 파일을 바꾸는 이유를 알려준다.
3. 해당 단계를 구현하고 핵심 diff를 설명한다.
4. 작은 입력 예시와 기대값으로 코드 흐름을 설명한다.
5. 필요한 테스트를 실행하고 명령, 결과, 검증 한계를 알려준다.
6. 완료한 내용과 다음 단계를 정리하고 멈춘다.

내가 “다음 단계 진행해줘”라고 하기 전에는 다음 단계로 넘어가지 마.
기존 작업은 보존하고, 설명은 처음 보는 코드도 따라갈 수 있게 해줘.
```

이 요청은 첫 단계의 수정과 검증까지 포함한다. 수정 전에 설계부터 검토하고 싶다면 다음 문장을 대신 사용한다.

```text
이번에는 설계만 설명해줘.
목적, 입력과 출력, 수정 예정 파일, 테스트 계획까지 보여주고 멈춰줘.
내가 “설명한 첫 단계를 구현해줘”라고 하기 전에는 파일을 수정하지 마.
```

## 2. 한 단계의 크기와 역할

한 단계는 “입력 하나의 유효성을 검사하기”, “계산 하나와 그 검증 완성하기”처럼 결과를 설명하고 확인할 수 있는 동작으로 잡는다. 함수 하나가 출발점이 될 수 있지만, 관련 계약·템플릿·문서·테스트를 함께 바꿔야 한다면 하나의 단계에 포함한다.

단계 수나 파일 수는 고정하지 않는다. 설명을 따라가기 어려워지면 구현 전에 범위를 줄인다. 전체 기능은 저장소의 수직 흐름을 완성하는 방향으로 쌓는다.

| 시점 | 에이전트가 보여줄 내용 | 사용자가 확인할 내용 |
|---|---|---|
| 시작 | 현재 상태, 이번 단계의 목적과 완료 기준 | 지금 해결하려는 문제가 무엇인지 |
| 수정 전 | 파일 경로, 역할, 변경 이유 | 어느 계층의 책임인지 |
| 수정 후 | 핵심 diff, 입력에서 출력까지의 흐름 | 무엇이 달라지고 왜 필요한지 |
| 검증 후 | 명령, 기대값, 실제 결과, 남은 한계 | 어떤 동작까지 확인했는지 |
| 단계 종료 | 완료 내용, 미완료 내용, 다음 단계 | 질문할지 다음 단계로 갈지 |

기본 방식에서는 계획을 설명한 뒤 해당 단계의 구현과 검증을 진행한다. 단계 내부의 모든 명령마다 승인을 받는 방식은 아니다. 별도로 “수정 전 정지” 또는 “파일 하나씩 수정 후 정지”를 요청하면 그 지점에서 멈춘다. 계약 변경처럼 여러 파일을 함께 맞춰야 하는 작업을 나눠 볼 때는 중간 상태가 미완료임을 표시한다.

## 3. 변경 내용을 읽는 순서

한 단계가 끝나면 다음 순서로 살펴본다.

1. **목적:** 이 변경이 어떤 문제를 해결하는지 한 문장으로 읽는다.
2. **입출력:** 함수나 데이터가 무엇을 받아 무엇을 내보내는지 확인한다.
3. **테스트 예시:** 작은 입력과 기대값을 먼저 보고 동작을 예상한다.
4. **핵심 diff:** 그 동작을 만드는 변경 줄과 주변 코드를 읽는다.
5. **실패 처리:** 결측, 잘못된 입력, 경계값에서 어떻게 행동하는지 확인한다.

`diff`는 수정 전후의 차이다. 보통 `+`는 추가한 줄, `-`는 제거한 줄이며, `+++`와 `---`로 시작하는 파일 표시는 실제 코드가 아니다. 익숙하지 않은 문법은 해당 줄을 지정해서 질문한다.

에이전트에게는 다음 형식으로 단계 결과를 요청할 수 있다.

```text
이번 단계:
목적과 완료 기준:
변경 파일과 역할:
핵심 diff와 변경 이유:
입력 → 처리 → 출력 예시:
테스트 명령과 실제 결과:
검증하지 못한 내용 / 아직 미구현인 내용:
내가 확인할 핵심 질문:
다음 단계 제안:
현재 상태: 사용자 확인을 기다리며 정지
```

## 4. 내 컴퓨터에서 변경 확인하기

편집기에서 저장소 폴더를 열고, 이번 단계에서 안내받은 구현 파일과 테스트 파일을 나란히 본다. PowerShell에서는 먼저 작업 위치를 맞춘다. 저장소를 옮겼다면 실제 경로로 바꾼다.

```powershell
Set-Location -LiteralPath 'C:\Users\kuri\OneDrive\versionedfinancecore'
git status --short
```

`git status --short`의 `??`는 Git에 아직 등록되지 않은 파일이다. `M`은 수정, `A`는 추가 상태를 나타내며, 두 상태 칸은 각각 스테이징 상태와 작업 폴더 상태를 나타낸다. 스테이징은 다음 커밋에 포함할 변경을 골라 두는 과정이다.

| 보고 싶은 내용 | 명령 |
|---|---|
| 전체 변경 상태 | `git status` |
| 추적 중인 파일의 아직 스테이징하지 않은 변경 | `git diff` |
| 위 변경의 파일별 규모 | `git diff --stat` |
| 스테이징한 변경 | `git diff --cached` |
| 특정 파일의 아직 스테이징하지 않은 변경 | `git diff -- src/versioned_finance_core/financial_core/identities.py` |
| 새 교본의 전체 내용 | `Get-Content -Raw -Encoding utf8 'docs/pair_programming_guide.md'` |

새로 만든 미추적 파일의 내용은 일반 `git diff`에 나타나지 않는다. `??`인 파일은 편집기나 `Get-Content`로 직접 연다. 차이가 출력되지 않았다는 이유만으로 변경이 없다고 판단하지 않는다. 파일 확인을 위해 `git add`를 실행할 필요는 없다.

문서 작성 시점에는 저장소의 기존 파일들도 미추적 상태였다. 따라서 전체 변경 목록과 이번 단계에서 에이전트가 실제 수정한 파일 목록을 구분해서 확인한다. 커밋할 때도 포함할 파일을 검토한 뒤 명시적으로 선택한다.

## 5. 테스트를 실행하고 이해하기

현재 프로젝트의 Python 요구사항은 3.11 이상이다. 아래 명령은 저장소 루트에서 실행한다. 먼저 이번 단계와 직접 관련된 테스트를 보고, 단계 완료 보고 전에는 저장소 필수 검증을 수행한다.

```powershell
# 예시: 기존 재무 항등식 테스트를 자세히 확인
python -m pytest tests/unit/test_financial_identities.py -v

# 저장소 필수 검증
python -m pytest
python -m compileall -q src

# ruff가 설치되어 있을 때 실행
ruff check src tests
```

위 명령은 사용자가 직접 확인하는 방법이다. 에이전트가 이미 검증을 마쳤다면 이해를 위해 필요한 명령만 다시 실행해도 된다.

`pytest`는 기대한 동작과 실제 결과를 비교한다. `compileall`은 Python 코드를 컴파일할 수 있는지 검사하며 재무 계산의 정확성을 증명하지 않는다. `ruff`는 코드의 정적 오류와 스타일 규칙을 검사한다. `compileall -q`는 성공 시 출력이 없을 수 있으며, 명령 직후 `$LASTEXITCODE`가 `0`인지 확인할 수 있다.

`No module named pytest`처럼 도구가 없는 오류는 테스트의 기대값이 틀렸다는 뜻과 다르다. 실행한 명령과 오류 메시지를 함께 전달해 환경 문제인지 코드 문제인지 먼저 구분한다. 필요한 개발 도구는 `pyproject.toml`의 `dev` 항목에 정의되어 있다.

테스트 결과를 볼 때는 아래 세 가지를 설명받는다.

- 어떤 입력에 대해 어떤 결과를 기대했는가?
- 실제 실행 결과가 기대값과 일치했는가?
- 이 테스트가 확인하지 않은 조건은 무엇인가?

계산 변경에는 unit, known-answer, boundary/missing-data, regression 검증을 포함한다. 각각 개별 동작, 정답이 알려진 예시, 경계·결측 처리, 기존 동작 보존을 확인한다. 구체적인 최소 검증은 `AGENTS.md`와 `implementation_playbook.md`를 따른다.

통과 개수만으로 전체 요구사항 구현이나 실제 회사 데이터의 타당성을 판단하지 않는다. 실행하지 못한 검증은 이유와 함께 미검증으로 남긴다.

## 6. 실제 코드로 따라 읽는 예시

다음은 이미 있는 함수를 읽는 학습 예시다. 새 구현이 완료되었다는 보고가 아니며, 숫자는 계산 검증용 합성 입력이다.

- 구현: [financial_core/identities.py](../src/versioned_finance_core/financial_core/identities.py)
- 검증: [test_financial_identities.py](../tests/unit/test_financial_identities.py)

`debt_face_rollforward_residual`은 기초 부채와 기간 중 변동을 더한 계산값이 입력된 기말 부채와 일치하는지 확인한다. 반환하는 `residual`은 두 값의 차이다.

```text
잔차 = 기초 부채 + 신규 차입·발행 + 기타 증감 - 원금 상환 - 기말 부채

기초 100, 신규 30, 기타 5, 상환 20이면 계산상 기말 부채는 115다.
기말 부채를 115로 입력하면 잔차는 0이다.
기말 부채를 114로 입력하면 잔차는 1이다.
```

기존 테스트 `test_identity_exposes_residual_instead_of_hiding_it`는 두 번째 경우의 결과가 `Decimal(1)`인지 검사한다. 이때 잔차가 1이어도 테스트는 통과한다. 불일치를 그대로 드러내는 것이 이 테스트의 기대 동작이기 때문이다.

다음 요청으로 함수 한 개부터 따라갈 수 있다.

```text
파일 수정 없이 debt_face_rollforward_residual과 대응 테스트를 설명해줘.
각 인자의 뜻, 계산 순서, Decimal을 쓰는 이유를 알려줘.
기말 부채가 115일 때와 114일 때를 비교해줘.
이 테스트가 확인하지 않는 조건도 짚어주고 멈춰줘.
```

잔차가 0이라는 사실은 주어진 입력들이 해당 항등식에 맞는다는 의미다. 원천 자료의 정확성, 공개시점, 단위, 다른 재무제표와의 일치는 별도의 검증 대상이다.

## 7. 이해 속도에 맞추는 요청문

| 상황 | 사용할 문장 |
|---|---|
| 설명부터 보고 싶다 | “파일 수정 없이 설계와 작은 예시만 설명하고 멈춰줘.” |
| 구현 범위가 크다 | “이번 단계의 범위를 동작 하나로 줄이고, 수정 전에 계획을 다시 보여줘.” |
| 코드가 어렵다 | “진행을 잠깐 멈추고 이 함수의 입력부터 반환값까지 한 줄씩 설명해줘.” |
| 재무 개념이 어렵다 | “코드 설명 전에 이 계산의 경제적 의미와 단위부터 설명해줘.” |
| 직접 코드를 써 보고 싶다 | “파일을 수정하지 말고 내가 작성할 함수의 입출력과 기대 동작을 알려줘. 작성한 뒤 리뷰를 부탁할게.” |
| 직접 테스트하고 싶다 | “내가 실행할 테스트 명령과 예상 결과를 알려주고 멈춰줘.” |
| 실패 원인을 먼저 배우고 싶다 | “테스트가 실패하면 수정하기 전에 명령, 기대값, 실제값과 원인을 설명하고 멈춰줘.” |
| 다음 단계로 가고 싶다 | “이번 단계 이해했어. 다음 한 단계만 구현·검증하고 멈춰줘.” |

질문하면서 구현도 멈추길 원하면 “진행을 멈추고” 또는 “파일 수정 없이”를 함께 말한다. 질문에 답한 뒤 계속 구현해도 되는 경우에는 “간단히 설명하고 현재 단계는 계속 진행해줘”라고 지정한다.

## 8. 이 프로젝트에서 함께 지킬 기준

이 교본은 협업 절차를 다룬다. 공통 데이터·version·interface·구축 순서는 [P0 마스터 설계서](../outline/P0_통합_기업재무_의사결정_시스템_마스터_설계서.md)를 우선하며, 구체적인 작업은 [AGENTS.md](../AGENTS.md), [아키텍처](architecture.md), [구현 플레이북](implementation_playbook.md)을 함께 따른다. 모듈 작업에는 M1=P1+P2, M2=P3, M3=P4 annex를 읽는다. `outline/` 원본은 사용자의 명시적인 요청 없이 수정하지 않는다.

구현을 검토할 때 특히 다음을 확인한다.

- 공통 재무 계산은 `financial_core`가 소유하고 M1·M2·M3가 필요한 출력을 소비하는가?
- 출처, 최초 공개시점, 조회시점, 기간, scope, 통화·단위와 version을 추적할 수 있는가?
- 결측을 0으로 채우거나 오차를 감추지 않고 의미에 맞는 상태로 표시하는가?
- 핵심 금액 계산에 `Decimal`을 사용하고 가정·충격·임계값의 근거를 남겼는가?
- 계약을 바꾸면 관련 템플릿, 문서, 테스트도 함께 갱신했는가?
- 원문 snapshot과 기존 release를 보존하며 실패한 release gate는 `WITHHELD`로 처리하는가?

구축 순서는 R0 증거·통제 기반 → R1 M1 Core → R2 M2 → R3 M3이며, 각 선행 gate를 확인하고 진행한다. 금융서비스 overlay는 해당 case의 적용 근거가 있을 때 선택적으로 활성화한다.

문서 작성 시점의 프로젝트 상태는 `SCAFFOLD_ONLY`이고, 대상 회사·분석 기준시점·분석 결론은 없다. 기존 코드와 합성 테스트의 존재를 실제 회사 분석이나 예측력 검증으로 표현하지 않는다. 테스트 예시에는 credential, 개인정보, 비공개 자료를 넣지 않는다.

## 9. 단계 종료와 다음 대화 재개

다음 단계로 넘어가기 전에 스스로 아래 항목을 확인한다.

- [ ] 이번 변경의 목적을 내 말로 설명할 수 있다.
- [ ] 수정한 파일과 각 파일의 역할을 안다.
- [ ] 작은 입력 예시의 결과를 예상할 수 있다.
- [ ] 어떤 테스트가 무엇을 확인했는지 안다.
- [ ] 아직 미구현이거나 검증하지 못한 부분을 안다.

막힌 항목이 있으면 해당 부분을 질문한다. 대화를 마칠 때는 아래 양식으로 인수인계 요약을 요청해 다음에 이어간다. 파일로도 남기고 싶으면 저장할 경로를 함께 지정한다.

```text
오늘 작업을 다음 대화에서 이어갈 수 있게 정리해줘.

현재 목표:
완료한 단계:
이번에 변경한 파일:
핵심 설계 결정과 이유:
실행한 검증 명령과 결과:
남은 문제와 미검증 사항:
내가 더 설명받고 싶은 부분:
다음 한 단계의 목적과 완료 기준:
재개 방식: 이 교본에 따라 다음 한 단계만 진행하고 정지
```

다음 대화에서는 교본 경로와 요약을 전달한다.

```text
docs/pair_programming_guide.md 방식으로 이어가자.
아래는 지난 작업 요약이야: [요약 붙여넣기]
현재 파일과 Git 상태를 확인해 요약과 달라진 점부터 알려줘.
이미 완료된 단계는 반복하지 말고 다음 한 단계만 진행해줘.
```
